# 首轮技术研究笔记｜从开源能力到工程判据

> 研究日期：2026-10-19。本文据各上游官方 README、LICENSE、仓库结构和 Ad Astra R2 底账形成**可验证的技术假设**。未执行上游项目构建或本地复现实验；案例的状态为 `SOURCE_CHECKED` / `ANALYSIS_DRAFT`，而非技术验证成功。索引见 [资料登记簿](source-register.md)。

## RN-01｜NASA NOS3：把“硬件暂不可用”变成可测试的软件输入

**原始依据**：[nasa/nos3 README](https://github.com/nasa/nos3/blob/main/README.md) — 系统提供软件设备模型、仿真环境、地面站、多目标构建及 V&V 开发环境。

**对本项目的真正启发**：不应该等到 EDF/舵机/传感器全部连接后才发现状态机如何处理异常。先定义可替换的“传感器输入边界”，再让软件在没有真实传感器时也能接收**已知的有效/无效输入流**，验证异常进入系统后的行为。

- **已有证据**：`flight_computer` 编译和 native 测试；`ground_station` 有模拟网络与 ACK/NACK 测试。
- **已知缺口**：`R0-005` 传感器初始化/读取失败处理不充分；`R1-002` 真实 USB/UART/WiFi/舵机链路无复现证据。
- **最小研究实验（只用离线软件）**：引入独立虚拟数据源，覆盖“设备缺席”“读取长度不足”“传感器值非有限数”“时间戳不连续”“消息丢失/重排”。记录每个输入对应的健康标志、状态转换及遥测解释。
- **验收判据**：每个异常用例具备输入、预期输出、测试结果和可复现命令；无效观测不得被错误标为正常数据；测试不会接通实际动作设备。
- **不能证明**：虚拟总线测试不证明物理传感器、I2C 时序或应急机构已验证，也不授权带动力的试验。
- **决策**：`TRANSFER_PROPOSED`（方法层）；不直接复制 NOS3 整个环境。复制代码前完成 NOSA 1.3 许可审查。

## RN-02｜NASA F´：飞控首先要有可单独验证的边界

**原始依据**：[nasa/fprime README](https://github.com/nasa/fprime/blob/devel/README.md)。其核心是组件、清晰接口、命令/遥测、消息线程与单元/集成测试。

**问题反推**：当固件的传感器采集、估计、状态机和通信都与真实平台 I/O 紧耦合，软件测试就难以覆盖故障模式。分层的首要收益不是“架构漂亮”，而是**隔离故障、确认数据的来源与有效性**。

**最小组件合同草案**：
- `SensorAdapter`：输出 `sample`、`timestamp`、`validity`、`fault_code`，不以某个值代替“未读取成功”。
- `Estimator`：仅消耗具名有效性输入；对输入不可用时的行为做明确测试。
- `Telemetry`：观测值与有效性状态一起编码；不得将模拟数据默认为实测。
- `CommandProcessor`：命令边界、授权来源、幂等/重放身份等单独验收。
- `HealthMonitor`：面向软件的异常集合与故障注入回执。

**研究限制**：这是对组件接口的**概念提议**，不是对现有代码的逐行审查或已经批准的重构。STM32F103 的 RAM/Flash 约束真实存在，**不要直接编译整个 F´ 进入当前固件**。

**验证出口**：在原生测试环境做兼容适配，保持既有生产行为；证明无效输入不会静默流入状态估计；提供基准分支对照测试和资源占用差异。状态 `TRANSFER_PROPOSED`。

## RN-03｜RocketPy：从“有仿真曲线”转为“可信结论”

**原始依据**：[RocketPy README](https://github.com/RocketPy-Team/RocketPy/blob/master/README.md)：高功率模型火箭的 6DOF 轨迹建模、气象/回收与蒙特卡洛，README 提供验证论文及项目来源。

**与 Ad Astra 的关键区分**：
- `aero_sim/rocket_config.py` 是历史**固体模型火箭**构型，现阶段的 `AA-TVC-BENCH-001` 是**受限 EDF 机械/航电台架**。
- EDF 依赖大气，不能凭借 RocketPy 的电机/火箭模型直接代表 EDF 工作过程。
- `R0-008` 有动力学极性及假设冲突，`R0-009` 缺少完整结果来源。

**每次仿真必须登记**：
1. `intended_use`（用于回答哪个具体问题，**不支持什么决策**）；
2. `model_id/version`，坐标系及单位，假设与适用范围；
3. `source_commit`、完整配置/依赖版本及输入 SHA256；
4. 初始条件和随机种子、数值积分方法及误差设置；
5. 结果文件 SHA256、可复现命令、比较基准/局限和评审人。

**首个隔离任务**：使用无动力的数学基准案例（如常加速度/无阻力解析运动）验证积分、单位和坐标约定；针对现有仿真脚本分别建立符号反转、边界输入的回归测试。结果与历史产物分目录存放，避免覆盖历史。

**判据**：可复现 > 可比较 > 在声明的应用范围内有验证依据，才可称为“可信仿真”；未取得实物观测时保持 `PROTOTYPE`。状态：`ANALYSIS_DRAFT`。

## RN-04｜NASA IKOS：让代码审查补上机器能发现的错误

**原始依据**：[NASA IKOS README](https://github.com/NASA-SW-VnV/ikos/blob/master/README.md)：面向 LLVM/C/C++ 的静态分析，能够发现包括数组越界在内的部分运行时错误，并区分安全/错误/不确定。

**适用性**：当前固件包含命令解析、I/O 缓冲与状态机；已有 native 测试不等于所有输入路径无未定义行为。

**隔离试验计划**：
- 在**独立 Linux/容器测试环境**选择现有可编译的纯 C/C++ 单元及无硬件依赖逻辑；
- 将静态分析工具版本固定、记录完整命令与报告；
- 关注越界、除零、非法内存访问、未初始化及整数异常；对每个诊断人工核对真/假阳性及修复证据；
- 不能解析的板级库/硬件依赖明确列入覆盖缺口；不得将“0 warning”解释为整个飞控可用于飞行。

**停止条件**：编译工具链无法可靠产出所需中间表示时，标记 `BLOCKED_TOOLCHAIN`，不在生产分支上大规模改动。状态：`TRANSFER_PROPOSED`。

## RN-05｜CadQuery：参数化不等于机械可制造

**原始依据**：[CadQuery README](https://github.com/CadQuery/cadquery/blob/master/README.md)、[LICENSE](https://github.com/CadQuery/cadquery/blob/master/LICENSE)。支持脚本参数化、装配/STEP 等多种 CAD 输出；官方许可为 Apache-2.0。

**当前相关问题**：`R0-011` 混杂历史 CAD 构型，`R0-012` 验证脚本成功退出不代表几何合同通过。

**必须分成四个关卡**：
1. **参数关**：每个数字对应项目批准的实物测量/需求或明示的未确认占位；统一 mm、datum 和坐标系。
2. **几何关**：模型非空、拓扑/闭合一致，关键装配接口得到检查。
3. **机械关**：实体运动、装配可达、布线余量、公差和紧固/拆卸路径待独立审查；不能仅用单一网格展示替代。
4. **工程验证关**：材料、力学载荷、制造、实物装配均需独立证据与审批。

**首阶段不允许**：根据历史 74mm、±15°、M3 类参数自动输出“当前正式机架”；R2 缺失参数继续阻断。**首阶段可做**：编写无实物依赖的参数字典、输入检验及导出 provenance 约束；AeroForge 的 CAD 申请入口只读审阅。

**验收判据**：失败的几何/接口断言使验证命令非零退出；输出包含实体名、模型版本、输入测量 IDs 与 hash，不误报 manufacturing-ready。状态：`TRANSFER_PROPOSED`。

## RN-06｜NASA-STD-7009B：仿真可信度是“使用场景特定”的

**原始依据**：[NASA-STD-7009 官方页](https://standards.nasa.gov/standard/NASA/NASA-STD-7009)，另有 [2026 NASA-HDBK-7009B 实施指南](https://standards.nasa.gov/standard/NASA/NASA-HDBK-7009)。

**关键方法**：
- 模型并非“验证一次就所有场景正确”；需明确 intended use、边界、输入质量、假设、数值误差和不确定性。
- 计算结果被用来做不同风险的决策时，可信性要求不同。
- 完整披露“还不知道什么”比给出看似准确的 4 位小数更有工程价值。

**针对当前研究**：`aero_sim`、`dynamics_sim` 的每个输出先增加适用范围和来源审查，再考虑进一步优化模型复杂度。状态 `ANALYSIS_DRAFT`，不是标准合规声明。

## RN-07｜NASA cFS、FRET、OpenMDAO 的使用顺序

- [cFS](https://github.com/nasa/cFS)：README 明确警告公开 demo bundle **not flight distribution / not fully verified**。学习其健康管理、系统抽象和应用分层，但目前不移植整个框架。
- [FRET](https://github.com/NASA-SW-VnV/fret)：可以参考其需求语义精确化与测试用例的联系；先在受控项目需求中试点“一个要求对应可验证判据”，无需立即部署复杂软件。
- [OpenMDAO](https://github.com/OpenMDAO/OpenMDAO)：如果输入参数的真实来源不明确，优化求解器只会高效地优化一个不可信模型。放在参数、模型与证据稳定之后。

## 阶段结论

应当**先迁移验证思想，再评估复用依赖和源代码**。当前可优先研究的工程收益：
1. 软件故障数据可重复输入、预期结果可审查；
2. 数据来源/有效性跨模块保留；
3. 仿真模型结果具备完整追踪；
4. CAD 输入与实物测量建立约束；
5. 每一个失效、警告和阻断都不能被 UI 或“PASS”字样掩盖。

以上还只是源码/原始资料级研究起点。具体实现必须另开受控提案，并经过各自项目规定的审查与回归。
