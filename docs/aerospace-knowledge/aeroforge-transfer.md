# 面向 AeroForge 的受控知识迁移合同｜非实施文档

> 更新 2026-10-19。当前仍属 **Ad Astra 研究提案**，不是 AeroForge 已实施功能。  
> 参照 [AeroForge 项目定义](https://github.com/guo6x/aeroforge-engineering-os/blob/main/README.md)、[其正式 L0-L5 定义](https://github.com/guo6x/aeroforge-engineering-os/blob/main/docs/25_final_product_definition.md)。跨仓库的产品真实情况须在实施当日重新获取该仓库的最新主分支及权威文件。

## 核心原则

AeroForge 的价值不是“导入所有 GitHub 知识后 AI 就能设计火箭”，而是使知识与工程目标、版本、证据、审查形成数字线程。**研究事实、建议、批准要求、工程实际参数、实物验证与生产放行严格分开。**

当前应先建立只读/提案级接口，绝不通过新增研究知识绕过已有 `Brief → Proposal → 独立复核 → 受控应用` 流程及 L0-L5 阶段准入。

## 推荐的逻辑实体（未来设计时参考）

| 实体 | 最小字段 | 谁可以修改/批准 |
|---|---|---|
| `KnowledgeSource` | source_id、url、上游 SHA/tag、license、查阅时间、source_type、内容摘要 | 研究维护人员；仅表示原始资料 |
| `ResearchFinding` | finding_id、source_id、evidence_ref、适用条件、局限、research_status | 研究人员提交，复核确认状态 |
| `ProjectGapLink` | finding_id、project、issue_id、current_baseline、impact、优先级 | 受控需求/工程维护 |
| `ExperimentEvidence` | experiment_id、版本、环境、命令、输入/输出 hash、实测或模拟类型、结果 | 独立实验及复核，不自动提升工程等级 |
| `ChangeProposal` | proposal_id、关联 finding、受影响需求/接口、验收/回滚、评审状态 | 已有 AeroForge 提案与审批体系 |
| `ApprovalDecision` | 裁决者、时间、批准范围、受控版本、理由及签名/审计信息 | 与提交者隔离的现有审批角色 |

上面是**逻辑数据合同，不是强制新增数据库表**；优先复用 AeroForge 现有实体，不应因为知识库要求重复建设。

## 推荐从低风险只读能力开始

1. 在工程需求/问题界面展示“相关外部技术证据”，带来源版本、研究状态和风险。
2. 明确区分：`上游声称` / `阅读确认` / `本地软件复现` / `交叉验证` / `实物确认`。
3. 用户选择某条资料时，只允许生成**待审核技术提案**，而不是直接把外部参数同步到当前装备。
4. 提案自动关联原始 `engineering/` issue、必要的测试合同与当前基线 hash。
5. 实现失败时保留失败记录和原始技术假设，支持追踪“为什么没采用”。

## 先不要做的事

- 不因 GitHub 仓库上新就让 AI 自动改 CAD/飞控/推进链；
- 不自动更改项目 `UNKNOWN` 数据为任何网上型号尺寸或历史报告数字；
- 不由知识库的模型分数自动提升工程证据等级；
- 不让研究者、提案提交者与批准者是同一个逻辑角色；
- 不将第三方代码直接嵌入商业可分发安装包，除非许可证、供应链和安全审查已关闭；
- 不用在线检索结果直接触发实物试验、采购或放行。

## 第一轮产品端实际价值验证

以 `R0-009 仿真 provenance 缺失` 为试点最合适：
- 输入：`KnowledgeSource`（NASA 模型可信度方法、RocketPy）、`ProjectGapLink`（R0-009）；
- 输出：**只读**的研究说明、run-manifest 建议字段以及已有项目证据指针；
- 人工判断：是否同意为仿真生成器增加新的元数据记录；
- 验收：外部参考信息绝不更新设备参数，任何状态升级必须有真实本项目测试 evidence；
- 回退：关闭知识索引功能，原来的工程审批/参数/YAML 不改变。

可以并行做一个对 `R0-005` 的纯软件故障测试卡，但不能以此消除物理传感器故障验证门禁。

## 与未来“智能工程总师”的关系

真正可用的智能工程总师要能回答四类问题，并能提供证据：
1. 我们确实知道什么？原始证据在哪？
2. 哪些结论只是开源案例的设计思想？适用前提是什么？
3. 哪个当前项目问题值得解决？最小实验是什么？不做的代价是什么？
4. 实验和审批之后，是否应采纳、拒绝或继续等待？

这条链路的成功条件是可审计、可复现、可拒绝、可回滚，而不是“AI 似乎知道很多航天知识”。
